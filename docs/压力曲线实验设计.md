# 用压力曲线定位性能拐点

## 1. 目标

本阶段只通过端到端曲线回答：

1. 并发升高后，FS/slab 的 TTFT 在哪个区间开始明显恶化；
2. 吞吐在哪个区间开始收益递减；
3. slab 的低负载优势能否保持到更高并发；
4. 为下一阶段 C++ 归因选择拐点前、附近、后三个负载点。

TTFT 本来就混合了 I/O、后台 store、CPU 调度、内存拷贝和请求执行等影响。本阶段接受这种混合，只定位“现象出现在哪里”，不解释原因，也不使用“已经测得排队”或“已经找到具体瓶颈”的表述。

## 2. 固定条件

- 模型、软硬件版本、prompt/output 长度和 block size 不变；
- CPU primary 固定 64 MiB；
- slab 容量/QD、FS worker 数固定；
- 每个服务内完成同形状 JIT 预热，drain 后清空全部 KV tier；
- 正式窗口无 QPS 上限，使用闭环并发；
- FS/slab 使用完全相同的请求及顺序。

## 3. Mixed 请求

- 50% hot：预先存入 secondary，正式时触发 load；
- 50% cold：正式前不存在，正式时触发 store；
- 每个 prompt 唯一且只测一次，避免 load 后转成 GPU/CPU 命中；
- request ID 能关联 hot/cold 标签；
- 并发 ≥2 时，hot/cold worker 各占一半；
- 并发 1 只是顺序混合，不代表同时竞争。

请求数由 slab 容量反推，hot blocks、cold blocks 和安全余量之和不得超过容量。容量不足时增加独立 arm，不能复用 prompt。

## 4. 单个 arm

```text
启动服务
→ 同形状 mixed JIT 预热
→ drain，清空 GPU/CPU/secondary
→ 预填 hot，等待 store 完成
→ 只清 GPU/CPU，保留 secondary
→ 验证 hot resident、cold absent
→ 清空监控窗口
→ 无 QPS 限速运行正式 mixed
→ drain、保存结果、停止进程组
```

正式窗口出现新 JIT、状态清理失败、请求分类错误或监控缺失则 arm 无效。正式压力导致的 primary/job 失败属于结果，不能删除。

## 5. 实验矩阵

先跑 `FS/slab × concurrency 2` 烟雾测试。

粗扫并发 `1,2,4,8,16`，每点各跑一个 FS/slab，并交替先后顺序。16 仍没有明显变化则逐次追加 32、64。

根据曲线选择：

- `C_low`：TTFT 尚稳定的最后一个点；
- `C_knee`：TTFT 明显恶化或吞吐开始收益递减的点；
- `C_high`：拐点后的第一个点。

取 FS/slab 候选点的并集，只对这些点做至少三轮镜像交错和 paired bootstrap CI。

## 6. 观察指标

- achieved throughput；
- hot/load 与 cold/store 分开的 TTFT P50/P95/P99；
- 现有 load/store job 平均 block 时间；
- primary 预留失败、load/store 完整 job 成功 block 数；
- 请求失败和正式窗口新增 JIT。

job 和 primary 指标只用于描述同时发生的现象，目标 2 不用它们完成底层因果归因。

## 7. 选取拐点

并发翻倍时，若 TTFT P95 明显上升而吞吐增长开始放缓，就把该区间列为候选拐点。阈值只用于辅助选区，最终展示完整曲线，不强行证明它由排队造成。

完成目标 2 的标准是：找到稳定复现的端到端性能拐点，并排除 JIT、QPS 限速、旧 secondary 数据和客户端不足等实验污染。之后再在 `C_low/C_knee/C_high` 上设计 C++ 指标，分解具体原因。
